# Спецификация системы спортивной аналитики и поиска Value Bets

**Версия:** 1.0  
**Статус:** проектирование  
**Язык:** Python + React  
**Основная задача:** анализ спортивных событий, расчёт вероятностей, поиск недооценённых букмекерских коэффициентов и формирование рекомендаций по ставкам.

---

# 1. Цель проекта

Разработать систему спортивной аналитики, которая собирает статистику, результаты, коэффициенты, составы, травмы и новости, анализирует предстоящие матчи и определяет потенциально выгодные ставки (Value Bets).

Система должна объединять:

- математические и статистические модели;
- алгоритмы машинного обучения;
- анализ букмекерских коэффициентов;
- LLM для обработки новостей и контекста;
- механизм поиска Value Bets;
- формирование ординаров и экспрессов;
- управление игровым банком;
- историческое тестирование моделей;
- мониторинг качества прогнозов.

Система не должна автоматически размещать ставки. Она формирует рекомендации, а решение о ставке принимает пользователь.

# 2. Поддерживаемые виды спорта

Первая версия должна поддерживать пять видов спорта:

1. Футбол.
2. Теннис.
3. Баскетбол.
4. Волейбол.
5. Хоккей.

Архитектура должна позволять добавлять новые виды спорта без существенного изменения общей системы.

Возможное расширение — настольный теннис.

Для каждого вида спорта предусматривается отдельная математическая модель, набор признаков и правила оценки качества данных.

# 3. Основные функциональные возможности

## 3.1. Сбор спортивных данных

Система должна автоматически собирать:

- расписание матчей;
- результаты;
- статистику команд;
- статистику отдельных игроков;
- историю встреч;
- текущую форму;
- рейтинги команд и игроков;
- составы;
- травмы и дисквалификации;
- информацию о турнирах;
- игровые события;
- букмекерские коэффициенты;
- новости и дополнительную информацию.

## 3.2. Анализ матчей

Для каждого предстоящего матча система должна:

1. Получить доступные статистические данные.
2. Проверить качество и актуальность данных.
3. Рассчитать базовые вероятности исходов.
4. Получить актуальные букмекерские коэффициенты.
5. Рассчитать рыночные вероятности.
6. Найти расхождения между моделью и рынком.
7. Проверить наличие новостей и изменений состава.
8. Оценить влияние новых факторов.
9. Пересчитать прогноз при необходимости.
10. Сформировать итоговую рекомендацию.

## 3.3. Поиск Value Bets

Система должна определять ситуации, когда букмекерский коэффициент недооценивает вероятность события относительно собственной модели.

Пример:

- коэффициент букмекера: 2.20;
- вероятность по модели: 50%;
- вероятность, заложенная в коэффициент: 45.45%.

Модель считает, что событие может иметь положительное математическое ожидание.

## 3.4. Формирование ставок

Система должна предлагать:

- ординары;
- экспрессы максимум из двух событий.

Для экспрессов необходимо проверять корреляцию между событиями и рассчитывать совместную вероятность.

Экспресс не должен формироваться исключительно ради увеличения общего коэффициента.

## 3.5. Пересмотр прогнозов

Если после первоначального анализа появляются новые данные, система должна:

- обнаружить изменения;
- определить, какие матчи затронуты;
- оценить достоверность новой информации;
- определить потенциальное влияние на признаки модели;
- пересчитать вероятность;
- сравнить новый прогноз с предыдущим;
- обновить рекомендацию;
- сохранить историю изменений.

Старые версии прогнозов не удаляются и не перезаписываются.

# 4. Архитектура системы

Предлагается модульная архитектура с отдельными логическими компонентами.

На начальном этапе рекомендуется использовать модульный монолит, а не создавать множество микросервисов.

## 4.1. Основные компоненты

### 1. Data Collection Layer

Отвечает за получение информации из внешних источников:

- спортивные API;
- букмекерские API;
- новостные источники;
- официальные сайты турниров и команд.

### 2. Data Quality Layer

Отвечает за:

- нормализацию данных;
- проверку обязательных полей;
- устранение дубликатов;
- проверку временных меток;
- сопоставление команд и игроков;
- контроль полноты данных;
- определение устаревшей информации.

### 3. Data Platform

Централизованное хранение:

- матчей;
- результатов;
- статистики;
- коэффициентов;
- новостей;
- прогнозов;
- истории изменений.

### 4. ML Engine

Математические и статистические модели.

Рассчитывает вероятности исходов на основании исторических данных и текущих характеристик матча.

### 5. AI Engine

Использует LLM для анализа новостей, контекста, составов и других неструктурированных данных.

LLM помогает выявлять факторы, которые могут быть не отражены в стандартной статистике.

### 6. Decision Engine

Основной модуль принятия решений.

Выполняет:

- сравнение вероятностей модели и рынка;
- расчёт EV;
- поиск Value Bets;
- проверку рынков;
- формирование экспрессов;
- оценку риска;
- управление банком.

### 7. Backtesting & Evaluation

Отвечает за проверку моделей на исторических данных.

### 8. Backend API

Предоставляет данные интерфейсу и внешним интеграциям.

### 9. Frontend

Веб-интерфейс пользователя.

### 10. Monitoring & Operations

Мониторинг работоспособности, ошибок, качества данных и расходов на LLM.

Предлагается пять ролей.
News Classifier
Классифицирует новость:
- травма;
- дисквалификация;
- состав;
- тренер;
- мотивация;
- конфликт;

Проверяет:
- подтверждается ли информация;
- есть ли другие источники;
- существуют ли противоречия;
- насколько надёжен источник;
- является ли новость актуальной.

Формирует контекстный анализ матча.
Critical Analyst
Пытается опровергнуть первоначальный прогноз.

Задаёт вопросы:
- Какие факторы модель могла не учесть?
- Какие данные противоречат прогнозу?

Формирует понятный отчёт для пользователя.

Важно: это логические роли, а не обязательно пять отдельных моделей. На старте достаточно одной-двух моделей с разными задачами.

7.5. Как новости влияют на прогноз
Принципиально важно: LLM не должна самостоятельно решать, что вероятность победы необходимо изменить, например, с 55% на 47%.

LLM должна извлечь и классифицировать факты.

Дальнейшая обработка:
1. Новость поступает в AI Engine.
2. News Classifier определяет тип новости.
3. Fact Checker проверяет достоверность.
4. Impact Assessment определяет затронутые признаки.
5. Python-модуль обновляет признаки матча.
6. ML Engine пересчитывает вероятность.
7. Decision Engine пересчитывает EV.
8. Система сравнивает новую и старую рекомендации.
9. Результат сохраняется как новая версия прогноза.
Числовое влияние должно определяться статистической моделью, а не произвольным мнением LLM.
7.6. Мониторинг новостей
Начальная стратегия:
- регулярно проверять новости по предстоящим матчам;
- ориентировочно каждые 10–15 минут для матчей в ближайшем временном окне;
- чаще обновлять составы по мере приближения матча;
- пересчитывать только матчи, затронутые новыми данными.
Частота должна учитывать лимиты API и фактическую скорость появления информации.

9.2. Расчёт вероятности из коэффициента
Для десятичного коэффициента:

P_implied = 1 / odds

Например, при коэффициенте 2.00:

P_implied = 1 / 2.00 = 0.50

То есть 50%.

Однако букмекерская линия включает маржу.

Для рынка с несколькими исходами необходимо оценивать вероятность после удаления маржи.

Простейший способ:

P_fair_i = P_implied_i / sum(P_implied_all_outcomes)

Это базовый метод нормализации, который можно заменить более точными методами при необходимости.
9.3. Expected Value
Формула:

EV = P_model * odds - 1

Пример:
- вероятность по модели: 0.55;
- коэффициент: 2.10.
EV = 0.55 * 2.10 - 1 = 0.155

Математическое ожидание составляет 15.5% на единицу ставки при условии, что вероятность модели верна.

Положительный EV не означает гарантированный выигрыш.

Необходимо учитывать:
- качество данных;
- свежесть данных;
- калибровку модели;
- неопределённость вероятности;
- наличие состава;
- новости;
- движение коэффициентов;
- расхождения между источниками.
9.4. Фильтр Value Bets
Система должна иметь настраиваемые фильтры:
- минимальный EV;
- минимальная уверенность модели;
- минимальное качество данных;
- минимальный уровень калибровки;
- максимальная неопределённость;
- минимальная ликвидность или доступность рынка;
- минимальная свежесть коэффициента.
Если данные недостаточны, рекомендация не должна формироваться.
9.5. Экспрессы
Максимум два события.

Для независимых событий:

P_joint = P_1 * P_2

Odds_parlay = Odds_1 * Odds_2

EV_parlay = P_joint * Odds_parlay - 1

Для зависимых событий нельзя просто перемножать вероятности.

Примеры возможной зависимости:
- победа команды и тотал этой команды;
- победа команды и фора;
- индивидуальная статистика игрока и результат его команды;
- несколько рынков одного матча.
В таких случаях необходима оценка совместной вероятности.

Перед формированием экспресса система должна:
1. Проверить совместимость рынков.
2. Проверить корреляцию.
3. Оценить совместную вероятность.
4. Рассчитать общий коэффициент.
5. Рассчитать EV.
6. Сравнить результат с ординарами.
7. Отказаться от экспресса при недостаточной уверенности.
10. Управление банком
Начальная конфигурация:
Параметр	Значение
Стартовый банк	1 000 ₸
Резерв	70%

Игровой лимит	30%
Игровой лимит в деньгах	300 ₸

Максимум событий в экспрессе	2

Все параметры должны быть конфигурируемыми.

Это стартовая схема, а не обязательная рекомендация по управлению реальными деньгами.

Правила:
- резерв не используется для отыгрыша;
- догон запрещён;
- не требуется расходовать весь игровой лимит;
- отсутствие Value Bets означает отсутствие ставок;
- экспрессы не должны формироваться ради большого коэффициента;
- количество ординаров не является обязательной квотой.
На начальном этапе использовать фиксированный размер ставки.

Дробный Kelly можно рассматривать позднее, после проверки качества и калибровки моделей, с дополнительными ограничениями риска.
11. Backtesting и оценка качества
Backtesting обязателен.

Система должна проверять, насколько хорошо модели работали бы на исторических данных.
11.1. Необходимые данные
- исторические матчи;
- результаты;
- статистика;
- исторические коэффициенты;
- составы;
- доступные на тот момент новости.
Особенно важна история коэффициентов.

Без исторических котировок нельзя достоверно оценить доходность стратегии.
11.2. Методика тестирования
Использовать:
- time-based train/test split;
- walk-forward validation;
- исторические симуляции;
- paper betting.
Запрещено использовать в прогнозе информацию, которая появилась после начала матча.

Это называется data leakage и приводит к искусственно завышенным результатам тестирования.
11.3. Метрики
Метрика	Назначение
Brier Score	Качество вероятностей
Log Loss	Качество вероятностного прогноза
ROI	Доходность
Yield	Доходность на сумму ставок
CLV	Сравнение с закрывающим коэффициентом

Нельзя оценивать модель только по проценту угаданных исходов.

21. Главный принцип архитектуры
Система должна строиться вокруг математической модели и качественных данных.

Распределение ответственности:
Компонент	Ответственность
Data Engine	Собирает и проверяет данные
ML Engine	Рассчитывает вероятности
AI Engine	Понимает новости и контекст
Decision Engine	Принимает решения на основе вероятностей и коэффициентов
Backtesting	Проверяет качество решений
Frontend	Показывает результаты пользователю

LLM не должна самостоятельно назначать вероятности и принимать решения о ставках.

Она должна помогать системе понимать новые факты, выявлять важные обстоятельства и передавать структурированную информацию математической модели.

Главный приоритет — качественные данные, исторические коэффициенты, корректная математическая модель и честный backtesting. Только после этого имеет смысл усложнять AI-анализ и автоматизацию.
